# MAX Chat · GREEN-API

Веб-сервис на **React + TypeScript + Vite** для отправки и получения текстовых
сообщений в мессенджере **MAX** через **[GREEN-API](https://green-api.com/max)**.
Интерфейс ориентирован на [web.max.ru](https://web.max.ru/): список чатов
слева, переписка справа.

Сделано только под MAX (без WhatsApp/Telegram-веток) — код и подписи в
интерфейсе не пытаются быть «универсальными под любой мессенджер», а прямо
завязаны на особенности API MAX (см. раздел про `chatId` ниже).

## Возможности

- Вход по `idInstance` / `apiTokenInstance` (проверяются запросом `GetStateInstance`),
  с человекочитаемой расшифровкой статуса инстанса и фоновой перепроверкой раз
  в минуту — если инстанс заблокируют или разлогинят прямо во время работы,
  пользователь увидит баннер, а не тишину.
- Создание нового чата по номеру телефона получателя — номер резолвится в
  настоящий `chatId` методом [`CheckAccount`](https://green-api.com/v3/docs/api/service/CheckAccount/)
  (в MAX `chatId` — непрозрачный числовой идентификатор, а не `phone@c.us`, как
  в WhatsApp — см. раздел «Устройство chatId» ниже).
- Отправка текстовых сообщений — метод [`SendMessage`](https://green-api.com/v3/docs/api/sending/SendMessage/),
  с повторной отправкой одним кликом при сбое.
- Получение входящих сообщений в реальном времени — long polling
  [`ReceiveNotification` / `DeleteNotification`](https://green-api.com/v3/docs/api/receiving/technology-http-api/).
- История переписки и учётные данные сохраняются в `localStorage` браузера
  (никакого бэкенда — запросы уходят из браузера напрямую в GREEN-API).

Список того, что **сознательно не реализовано** (по ТЗ — «максимально простой
интерфейс с минимальным набором функций»): вложения, группы, статусы
прочтения, редактирование/удаление сообщений.

## Что сделано для устойчивости к сбоям

Это не просто демо «happy path», а код, рассчитанный на реальные условия сети
и реальное поведение GREEN-API:

| Проблема | Как обработана |
|---|---|
| Сеть моргнула / GREEN-API не ответил вовремя | Таймаут на каждый запрос + классификация ошибок (`network`/`timeout`/`auth`/`rate_limit`/`server`) |
| Транзиентный сбой (5xx, 429, обрыв сети) | Автоматический ретрай с экспоненциальным backoff и джиттером — но НЕ для 4xx (неверный токен и т.п., это не чинится повтором) |
| Long polling падает раз за разом | Экспоненциальный backoff цикла опроса (до 30 с), баннер «переподключаемся» после 3 неудач подряд |
| Несколько вкладок с одним инстансом одновременно | Web Locks API — реально опрашивает очередь только одна вкладка, остальные не воюют за неё |
| Размонтирование компонента во время долгого long polling | Настоящий `AbortController`, а не флаг, ждущий до 20+ секунд |
| Неожиданная/неполная форма ответа вебхука | Defensive-парсинг с проверкой обязательных полей — просто пропускаем и логируем, не падаем |
| Дубли входящих сообщений (например, при переотправке недоставленного `DeleteNotification`) | Дедупликация по `idMessage` |
| Разросшаяся история чата (риск исчерпать квоту `localStorage`) | Обрезка истории до 500 сообщений на чат, а при `QuotaExceededError` — повторная попытка с агрессивной обрезкой |
| `localStorage` недоступен (приватный режим, отключённые cookies) | Все операции хранения — no-op с fallback, приложение продолжает работать в рамках сессии |
| Битый/устаревший JSON в `localStorage` | Схема версионируется, парсинг защищён try/catch, невалидные данные тихо игнорируются |
| Сбой отправки сообщения | Сообщение помечается статусом «ошибка» с кнопкой «Повторить отправку», не теряется |
| Неожиданная ошибка рендера React | `ErrorBoundary` — понятный экран с кнопкой перезагрузки вместо белого экрана |
| Слишком длинное сообщение | Клиентская проверка лимита длины (4096 симв.) до отправки |
| Опечатка в `idInstance` | Валидация формата (только цифры) прямо в форме входа |

## Стек

React 19, TypeScript (строгий режим: `strict`, `noUncheckedIndexedAccess`,
`noUnusedLocals`), Vite, обычный CSS. `npm run build` сначала гоняет
`tsc --noEmit` — сборка с ошибками типов не пройдёт.

## Локальный запуск

Требуется Node.js 18+.

```bash
npm install
npm run dev
```

Приложение откроется на `http://localhost:5173`.

Полезные команды:

```bash
npm run typecheck   # только проверка типов, без сборки
npm run lint        # oxlint
npm run build        # tsc --noEmit && vite build — так же собирается прод
npm run preview      # локальный просмотр собранного билда
```

## Как пользоваться

1. Зарегистрируйте инстанс в [личном кабинете GREEN-API](https://console.green-api.com/)
   и авторизуйте его в MAX (раздел инстанса → подключение / QR-код).
2. **Важно:** в настройках инстанса (`SetSettings` или личный кабинет) поле
   `webhookUrl` должно быть пустым, а `incomingWebhook` — включён. Иначе
   уведомления не попадут в очередь `ReceiveNotification` (см. диагностику ниже).
3. Откройте приложение, введите `idInstance` и `apiTokenInstance`. Если у
   инстанса указан отдельный хост API, разверните «Указать другой хост
   apiUrl» — иначе используется общий `https://api.green-api.com`.
4. Нажмите «Новый чат», укажите номер телефона получателя в международном
   формате без «+» (например `79991234567`).
5. Напишите сообщение и отправьте. Ответ собеседника из MAX появится в чате
   автоматически, без обновления страницы.

## Структура проекта

```
src/
  types.ts                      # общие типы (Credentials, ChatRecord, WebhookBody, ...)
  api/greenApi.ts               # HTTP-клиент: таймауты, ретраи, классификация ошибок
  hooks/useIncomingMessages.ts  # long polling входящих уведомлений с backoff
  hooks/useSingleTabLock.ts     # Web Locks API — одна вкладка опрашивает очередь
  context/AuthContext.tsx       # учётные данные, статус инстанса, фоновая перепроверка
  utils/storage.ts              # версионированная персистентность в localStorage
  components/                   # LoginForm, Sidebar, ChatWindow, MessageBubble,
                                 # NewChatModal, ErrorBoundary
  App.tsx                       # состояние чатов, отправка/ретрай, связка компонентов
```

## Устройство chatId в MAX (важно!)

В WhatsApp `chatId` всегда равен `номер_телефона@c.us`. В MAX (v3 API) это
**не так**: `chatId` — непрозрачный числовой идентификатор (например
`"10000000"`), который сервер MAX присваивает сам и никак не выводится из
номера телефона. Поэтому приложение не подставляет номер телефона напрямую в
`chatId`, а сначала резолвит его через
[`CheckAccount`](https://green-api.com/v3/docs/api/service/CheckAccount/) при
создании чата — и дальше и отправляет, и сопоставляет входящие сообщения
именно по этому значению. Подробнее:
[Важные отличия v3](https://green-api.com/v3/docs/important-differences/#chatid).

## Диагностика: сообщения отправляются, но ответы не приходят

1. **Настройки инстанса.** Убедитесь, что `incomingWebhook: yes` и
   `webhookUrl` пустой (личный кабинет или метод `GetSettings`).
2. **Консоль браузера (F12 → Console/Network).** Приложение крутит long
   polling `ReceiveNotification`/`DeleteNotification` в фоне; ошибки видны там.
3. **Несколько вкладок одновременно.** Решено через Web Locks API (см. таблицу
   выше), но если браузер его не поддерживает — держите открытой одну вкладку.

## Деплой (демонстрация в интернете)

В репозитории настроен workflow `.github/workflows/deploy.yml`: собирает
проект и публикует на **GitHub Pages** при push в `main`/`master`.

1. Запушьте код в свой репозиторий.
2. **Settings → Pages → Source: GitHub Actions**.
3. Ссылка появится во вкладке **Actions** и в разделе **Pages**
   (обычно `https://<username>.github.io/<repo-name>/`).

Альтернатива — импорт в [Vercel](https://vercel.com/new) или
[Netlify](https://app.netlify.com/start): команда сборки `npm run build`,
папка публикации `dist`. Это обычный статический SPA без бэкенда, подходит
любой статический хостинг.
